从 Python Agent 到 Copilot Harness：把 Microsoft Foundry 真跑一遍

2026年11月10日
 | Microsoft Foundry
 | 阅读

题图来源：Microsoft Foundry Blog

Agent 写完了，Python 写完了，数据接上了，模块之间怎么通信也调通了。然后话题转到了 harness 上。

GitHub、Microsoft Foundry 和 Copilot Studio（CPS）三家正在往同一套 harness 上收敛，也就是 GitHub Copilot harness。这件事落到具体做项目的人身上，问题就变得很具体：

我已经用代码搭好的那些 agent 怎么办？重写、包一层，还是留着？

与其抽象地争论，不如动手试一次。我手上正好有一个 Microsoft Agent Framework（MAF）的 demo，里面是 Python agent、Fabric 销售数据和产品知识。能不能保留有用的业务流程，把自定义的 agent 封装拆掉，让托管的 harness 多承担一些？

后来它变成了你现在看到的这个 demo。空白聊天框没什么可看的，这个 demo 更像个工作台：问业务问题、看工具到底被调了什么、顺着证据往下翻，最后把结论落成一份可以改也可以下载的简报。

我想回答的问题是：这个 agent 应用有多少能搬进 harness，有多少仍然必须留在我的代码里？

先说结论：我把一个基于 Python/MAF 的研究类 demo 迁到了 Foundry 托管的 Copilot harness 上，看它能不能应对同样的业务问题。原生检索和源连接确实减少了我需要编写的 agent 侧编排，而认证、流式输出和安全访问仍然由应用负责。可下载简报是我额外加的实验，不在原始迁移范围内。定向测试给出的结果不错，但它不足以证明功能已经完全对齐，也不代表可以上生产。

起点：用代码写的 agent

起点是 olivierb123/microsoftiq-lead-agent-demo。它用了四个托管的 Agent Framework 封装，扇出由应用控制：Python agent 代码和自定义的 source adapter 处理各类集成，应用决定调用哪个 agent，再把结果组装起来。

这种做法的好处是把编排摆在明面上；代价是托管封装、维护 source adapter、协调整个流程，责任全压在应用这一侧。

这次做 harness 实验，我保留了业务场景，换掉了执行模型。我没有在另一个服务里重建那些封装，而是配置了一个由 Foundry 托管的 Microsoft Copilot harness agent，给它 instructions、原生能力和已连接的源。

职责 用代码的 demo harness 实验
工作流编排 应用控制 agent 调用 托管 agent 自己选工具，也可以委派
研究 托管的封装和自定义 adapter 原生 web search 和页面读取
业务数据 应用侧源集成 原生 Fabric 连接
产品知识 应用侧检索集成 通过原生 MCP 做 Foundry IQ 知识库检索
工作产出 应用负责结果组装 对话工作区和已发布的 artifact
应用代码 UI 加 agent 编排 UI、认证、流式输出和会话与下载授权

仓库里是迁移后的实现。原来的代码 demo 单独保留，没有被覆盖。

一个实际问题，不是工具演示

场景是一个虚构的销售团队，配合 FieldForge 的产品文档。一个有用的助手应该能回答这样的问题：

扩展后的合成 demo 里有多少个未关闭的商机，总金额和按概率加权后的金额分别是多少，我们内部的预测口径又是怎么解释这些数字的？

这个问题需要两类不同的证据：结构化的商机数据，以及定义预测口径的那份内部文档。用户不应该被迫去点名某个 connector，或者规定工具调用顺序。

再复杂一点的请求，是要一份 South territory 的简报，把销售表现、重点商机、产品能力和官方的施工热暴露指引合到一起。用户接着可以在同一段对话里要求修改，或者要一份可下载的 Markdown 文件。

这些例子是把 harness 当成工作环境在用，而不只是一个文本生成接口。不过它们只是用来试探的请求，并不保证每一轮都会跑起每个工具或 subagent。

为什么先做本地 Web App

我特意把测试体验留在本地 Web App 里。提问、追问、看发生了什么，都应该很顺手，不必先把实验变成一个 Web 托管的项目。

React 工作台和 Node.js 后端跑在本地，agent 和已连接的源跑在云上。登录之后，我可以选一个示例问题，看着回答流式输出，查看 Activity 和 Evidence，然后在同一段对话里要求修改或下载。我不需要去还原一个原始的 SDK 响应，才能判断某个源到底有没有被调用。

这种分离也让迁移更容易理解。Web app 是测试面，不是 agent 的运行时。它背后没有本地 Python agent server 在偷偷干活：后端把请求发给 Foundry，并处理应用的认证、流式输出和会话内的下载。

第一版实验中，后端被刻意限制为只监听回环地址。把应用公开托管出去是另一项工程活，不是拿 harness 跑通一个真实场景的前提。

架构

配置好的 agent 使用 microsoft_copilot_preview 和 gpt-5-mini。agent 的定义放在 harness/azure.yaml 里，而不是某个 Python agent server 里。

应用、后端和数据脚本都是 JavaScript/Node.js。这一版不需要 Python 运行时、pip 安装或者虚拟环境。但这也不是零代码迁移：登录、token 校验、流式输出、会话归属和安全下载，仍然由应用自己负责。

后端不会再把原生源调用执行一遍。执行的是 Foundry，应用只是观察返回的结果，然后把它们呈现在 Activity 和 Evidence 里。

在 Foundry 门户里看到的样子

本地工作台只是这个实验的一个视角。Foundry 也支持托管的代码型 agent：我可以把自定义的 agent 代码（包括 Python/MAF 实现）和依赖打包进容器，让 Foundry 负责托管。agent 的实现和编排仍然归我，用 Python 不等于我必须自己跑 server。

这个实验用的是托管 harness 的 prompt agent：我配置它的 instructions、能力和源连接，Foundry 提供 harness 的执行环境和原生工具编排。两种方式都能在 Foundry 里跑。区别不在于本地还是云上，也不在于用不用 Python，而在于 agent 运行时和编排由我实现多少、交给托管 harness 多少。在这个 demo 里，应用的 UI、认证、会话与下载授权仍然是我的责任。

我的 microsoftiq-copilot agent 加上它配的工具和连接，就是上面那些变化的落点：架构图里的原生 harness 能力、Fabric 访问、产品知识检索，在这里被串成了一份配置。

这一版没有 Web IQ 封装

上一个 demo 里的 Web IQ 集成没有搬过来。外部研究走 harness 原生的 web search 去发现来源，再用它的 Web 能力读取相关页面。

这样就够支撑场景里的研究部分，不用再单独维护一个 Web IQ agent 封装。这不等于说原生 web 研究能复刻 Web IQ 的每一种行为和数据契约。

Fabric 和产品知识是可选的 grounding 来源，不是每个问题都必须经过的关卡。一个公开研究类的问题，就让它停在公开研究。私有业务数据不该被送进公开的 web 工具。

和 Fabric、Foundry IQ 更直接的集成

对我来说，集成的改善在于归属边界：harness 用的是配置好的原生连接，而不是去调用那些自己取凭证、自己查源的应用 adapter。

Fabric 提供结构化的业务事实。 原生 Fabric 连接用登录用户的上下文，访问一个建立在导入语义模型之上的专用 data agent。没有 app-only 的 Fabric 凭证兜底。模型里是演示数据，不是真实的 CRM 记录。

Foundry IQ 提供文档证据。 产品知识的 MCP 连接通向一个由 Azure AI Search 支撑的知识库。查询规划和语义检索返回的是可溯源的证据，包括存下来的文档元数据，供 harness 在回答里使用。这个连接用的是 Foundry 项目的托管标识；它并不建立按用户的文档 ACL 管控。

这个区别很重要。商机行里的 supportingDocId 只是一个关联引用，不能证明对应的文档真被检索到了。Fabric 替代不了知识库里的文档内容、标题或更新日期。

说这个集成「更好」，指的是更直接的原生集成、更清晰的源职责划分。我没有验证它在质量、延迟或成本上优于 MAF 实现，也没有验证过真正区分不同用户的授权。

实验到底展示了什么

定向测试表明，harness 能取出销售数字、找到内部文档、做 web 研究，并把对话继续下去。这正是我想从 MAF demo 里带过来的那部分工作流。

最有说服力的一个测试，是同时要销售数字和那份解释预测口径的内部文档。早期几次运行把数字算对了，但没有检索到要的那份文档。回答读起来很有说服力，可其中一部分解释缺少可验证的支撑。

在把 agent 的 instructions 说清楚、并明确哪个源该回答问题的哪一部分之后，有一次运行成功从两个源都取到了证据。用的是合成演示数据，不是真实客户信息。

教训是：把工具接上只是开始。还得测 agent 有没有用对的源，以及那些源是否真的支撑了它的回答。

迁移之外：工作区文件和简报

核心的问答流程在定向测试里跑通之后，我想试试 MAF demo 里没做的一件事：把一次回答变成一份可用的文档。

为什么要存一份简报？不是每个回答都需要。但一个 territory review 是个好例子：与其把分析留在聊天记录里，我可以要一份 Markdown 文档，留着、评审或者交给别人，然后在同一段对话里要求修改。文件是可选的交付物，不是取销售数据或产品证据的前提。

harness 的对话工作区和原生文件能力在这里变得有意思。我可以在托管环境里创建、读回、修改一个 artifact，而不必在 Python 封装里重建这些 agent 侧工具。MAF 配上合适的工具和代码也能支持同类流程；这是这个 demo 多出来的能力，不是 harness 独有的。

当用户真的想要下载时，发布是单独的一步。工作区里的文件不会自动变成可下载：只有原生上传返回了真实的 file ID，工作台才会登记它，而且只有那个未过期的会话所有者能下载。这些访问检查仍然由应用实现。

所以迁移问题是「我还能不能继续回答那些有用的业务问题」，扩展问题是「在 harness 的原生能力上我还能建什么」。简报帮我探第二个问题。真正说明创建、修改或发布有没有发生的是工具结果，不是助手自己的叙述。

还有几处运营上的边界。应用只监听回环地址，harness 还是 public preview，推理和检索都要花钱，工作区状态也不是持久化的应用存储。刷新浏览器或重启后端，本地的会话映射就丢了。生产托管、留存策略和更广的授权得另外做。shell 和对外部业务系统的写入仍然关闭。

结论

那么，我的 Python agent 怎么样了？在这个场景里，托管的封装不再需要了。业务问题还在，执行搬进了托管 harness，剩下的应用代码专注于体验和它的安全边界。

对这个实际的研究场景来说，工作重心从维护 Python 封装和固定的扇出，转向配置 agent、划分源的职责、打磨用户体验和验证证据。Fabric 和 Foundry IQ 直接嵌进了这个环境，原生 web 研究则在本文探索的这些任务上取代了原来的 Web IQ 路径。

什么时候我仍然会用 MAF

确定性路由与本地混合执行。 MAF 允许你部署混合拓扑：用小型本地模型（比如 MAI-Decision / Jev）做快速、确定性的分诊和工具门控，把昂贵的云端前沿模型留给复杂推理。托管 harness 会把所有路由锁进它的专有云运行时，你也就失去了优化延迟和 token 经济性的空间。

对编排循环的绝对控制。 Copilot Harness 用一个抽象过的推理引擎来决定何时启用一项技能、何时调用一个工具。

原生工具链的延续与托管。 MAF 的 agent 就是标准的 C# 或 Python 应用。

细粒度状态与语义记忆。 托管 harness 提供的是通用的共享记忆层。MAF 允许你自建记忆提供方，比如自定义 Azure SQL 或 Cosmos DB 的 schema。

不受限制的互操作机制。 Copilot Harness 能消费 Agent-to-Agent（A2A）协议和 Model Context Protocol（MCP）server，但在 MAF 里自己写 server 逻辑，你才能操作协议本身的机制。如果需要管理自定义消息头、为 SAP 或 ServiceNow 这类平台注入特定 token，或者在传输途中改动 payload 结构，MAF 给的是没有被抽象掉的那一层。

落到这个 demo 上，harness 让我不用再守着固定扇出，研究、连着的证据和 artifact 都进了同一个托管环境。换一个应用，继续留着它的 MAF agent 可能是更合适的选择。

我的结论很简单：从一个真实任务开始，把适合 harness 的职责搬过去，然后去测那条边界，而不是假设迁移一定成立。

下一步

这个实验只回答了一个问题，其他问题我还挺好奇：harness 在持续负载下表现如何？Fabric 的语义模型涨到生产规模会怎样？同一套办法能不能用在需要回写业务系统的 agent 上？如果你也在做类似的迁移，我很想知道哪些地方成了、哪些没成。

试试这个项目

代码在 olivierb123/microsoftiq-copilot-harness-demo。

挑一条路径：

  • 本地跑 demo，从 README 和 setup checklist 开始
  • 看 agent 配置，harness/azure.yaml 里是 Foundry 的 agent 定义
  • 理解数据模型，看合成数据的说明文档
  • 对比原来的 MAF 做法，看原来的代码 demo
